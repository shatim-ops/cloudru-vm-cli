# QA перед v1.0 — 2026-10-16

Аудитор: Claude Fable 5.1 (независимый QA), ночь 15→16.10.2026.
Ревизия: `main` @ `692e2fe` (после PR #45–#51). Прошлый аудит —
`FINAL_AUDIT.md` (`10ccc2c`, до rc.1): его утверждения перепроверены, не
переписаны. Код в этом PR не менялся — только отчёт.

Как проверялось: сборка и тесты в контейнере (Go 1.26.9), живой бинарь
без кредов (коды выхода, `--json`, гейты, MCP stdio и HTTP, миграция
старых путей), чтение кода с временными тестами (удалены), один прогон
`cloud-e2e` в `ru.AZ-1`. Кредов Cloud.ru в сессии не было, ресурсы
напрямую не создавались. Три направления (утечки ресурсов, цепочка
поставки, PR #45–#51) разбирали отдельные ревьюеры; их critical/high
я перепроверил по коду сам.

## Вердикт

**v1.0 не готов.** Сборка, тесты, CI, релизный конвейер, документация,
HTTP-политика MCP и коды выхода — в порядке (раздел «Что прошло»). Но
найдены три critical и три high в том, ради чего гейт и state вообще
существуют: обход подтверждения и двойное создание платных ВМ.

Блокеры тега `v1.0.0` (все — код, без облака воспроизводятся тестами):

1. `stack_plan` + `stack_status` создаёт ресурсы **без `confirmed=true`**
   (C1).
2. `stack_apply`: шаг `vm` при любой ошибке ответа `provision`
   (в том числе «не стала active за 5 мин») **создаёт ВМ повторно** —
   до четырёх ВМ с FIP на один шаг (C2).
3. `deploy_apply`: повтор с тем же `plan_id` ищет ВМ через `ListVMs`
   **без `project_id`**, который в этом тенанте не работает, и создаёт
   вторую ВМ (C3).
4. Три пути, на которых FIP или ВМ остаются без записи в state
   (H1–H3).

Остальное (medium/low) — на v1.0.1 или по решению владельца. Сквозной
прогон в `ru.AZ-1` — раздел «Облако».
