## Находки

**[high]** `internal/tools/tools_pg.go:400-410` — `pg_create` без `subnet_id` берёт `subs[0]` проекта без проверки зоны, тогда как `kafka_create`/`redis_create` идут через `dbaasSubnet` (`tools_kafka.go:110`) с предпочтением открытой зоны и отказом при закрытой. Путь: проект с первой подсетью в закрытой зоне (OPS-10, ru.AZ-1) → `pg_create name=x` → кластер уходит в `FAILED` → по DB-21 через API его не удалить (`pg_delete` → подсказка «удалите в консоли»). Это N-06, сознательно перенесённый в `[audit-90]`; считаю перенос ошибкой для v1.0: исправление — заменить блок выбора подсети на `dbaasSubnet(ctx, eng, stringArg(args, "subnet_id"))` (тот же код, что у Kafka/Redis), 5–10 строк. Гипотеза: тарифицируется ли кластер в `FAILED` — не знаю; даже если нет, это платный ресурс, застрявший вне контроля инструмента.

**[medium]** `internal/tools/tools.go:2131` (`destroyTargeted`) и `:1583` (`handleProvision`) — движок берётся из фабрики `mcpEngineFactory` → `buildEngine` (`internal/cli/main.go:279`) с `Printer = output.New(false, …)`, пишущим в `os.Stdout`; переопределение на буфер есть только у `deploy` (`:1487`), `logs` (`:2066`) и `destroy` текущего развёртывания (`:2102`). В stdio-режиме stdout — канал JSON-RPC (`internal/mcp/server.go:5-7` утверждает, что весь вывод движка перенаправлен — это не так). Путь: MCP stdio → `destroy vm_id=<ВМ с FIP> confirmed=true` → `ReleaseFloatingIP` → `e.Printer.StepDone("Floating IP … released")` (`internal/engine/destroy.go:324,329`) → строка `    Floating IP 1.2.3.4 (id) released` уходит в stdout перед JSON-ответом. Аналогично `provision`: `waitBootFIP` (`deploy.go:1006`, если FIP не привязался за 12 опросов) и `findBootFIP` (`:951`). Клиенты на официальных SDK логируют ошибку разбора и продолжают, но это нарушение протокола, и оно именно на денежных путях. Дефект не из диффа #89, но дифф усилил `destroyTargeted` и не закрыл его. Исправление: в `destroyTargeted` и `handleProvision` после `newEngine` ставить `eng.Printer = output.NewWithWriter(&buf, output.ModeText, false)`, как в `handleDeploy`; надёжнее — делать это один раз в `engineFor` для MCP-реестра. Подтверждено кодом, вживую не воспроизводилось.

**[medium]** `internal/tools/tools_stack.go:355` — отказ по `existing_id` считается чужим ресурсом только при `st.Attempts == 1 && !resumed`. Путь: шаг `pg`/`kafka`/`redis`/`k8s`/`vpc`/`lb`, попытка 1 падает ДО create (например, `check the name is free: list clusters: 5xx`, `list versions`), `findStepResource` ничего не находит, попытка 2 → инструмент отвечает `existing_id` на одноимённый ресурс, который существовал до стека → условие не срабатывает → `findStepResource` ищет по имени (для не-VM без проверки времени создания, `:112-119`) → чужой кластер «усыновлён» → `stack_destroy` его удаляет. Для VM защищает `created_time ≥ StartedAt-2m`; для остальных видов защиты нет. Гипотеза по вероятности: нужен транзиентный сбой до create плюс чужое одноимённое имя. Исправление: трактовать `existing_id` как чужой ресурс всегда, кроме случая, когда предыдущая попытка дошла до самого create (инструменты могут возвращать `create_sent: true` в ошибках после POST), либо сравнивать `created_at`/`createdAt` ресурса с `StartedAt`, как для VM.

**[low]** `internal/tools/tools_stack.go:81-99` — `findIDByName` (сверка не-VM шагов) не пропускает статусы `DELETED`/`ERASED`, в отличие от `takenName` (`namecheck.go:25-28`). Путь: повтор шага после сбоя при наличии удалённого одноимённого кластера → шаг `done` с id удалённого ресурса → следующие шаги падают. Исправление: тот же фильтр статуса.

**[low]** `internal/tools/tools.go:1866,1883` и `internal/engine/deploy.go:976-986` — `ReleaseBootFIP` при неудаче только печатает `Warning` (в MCP — в stderr сервера), а ответ инструмента говорит «nothing was created». Путь: загрузочный FIP создан → `CreateVM` отказал 409/422 → `DeleteFloatingIP` упал (сеть) → FIP тарифицируется, записи нет, агент видит «ничего не создано». Исправление: `ReleaseBootFIP` возвращает ошибку, `handleProvision` добавляет в ответ `floating_ip_id` и подсказку `release_floating_ip`.

**[nit]** `internal/provision/findvm.go:60` — `IsNameTaken` = любой 409; если 409 придёт по другой причине, текст «a VM named … already exists» будет неточен (исходная ошибка в цепочке сохранена). Можно сверять с `vm_with_this_data_already_exists` в теле.

## Проверено без замечаний

- Отказ API на create (4xx) → загрузочный FIP освобождается, одноимённая ВМ не усыновляется и запись не затирается (`provision.CreateRejected`, `deploy.go:523`, `tools.go:1861`, `deployplan/apply.go:165`); потеря ответа/таймаут → поиск по имени с `createStart` и запись в state.
- R-02: FIP, созданный после загрузки, попадает в state через замыкание `saveState` (`fipID` обновляется до записи `running`); при ошибке привязки — `status: partial`, `vm_ip: ""`, без строки SSH, код из ошибки.
- R-03/R-04: `destroyTargeted` сначала читает список, `vm_id` в приоритете, несколько одноимённых → `USAGE` с кандидатами, несуществующая → `VM_NOT_FOUND`, превью называет ВМ, FIP (released/kept и почему) и правила портов; без проекта → `CONFIG_INVALID`; запись другого проекта не удаляется.
- A-005/L-11: неподтверждённое удаление (CLI и MCP) оставляет запись `destroying` с FIP и правилами, код 5 / `status: partial`; `ActiveDeployment` (`state.go:174`) берёт любую запись кроме `destroyed`, так что повтор `evo destroy` доводит очистку; `release_ip=false` сохраняется в подсказке повтора; FIP, найденный по имени у незаписанной ВМ, записывается для повтора.
- FIP по адресу незаписанной ВМ освобождается только если имя соответствует `IsEvoFIPOf`, иначе сохраняется; при сбое `ListFloatingIPs` — «could not check», не «evo его не создавал».
- `disk_create attach_to=`: ожидание `available` до 2 мин, затем attach; неуспех — `partial` с `disk_id` и подсказкой `disk_attach`/`disk_delete`.
- `pg_create`/`kafka_create`/`redis_create`/`ar_create`: проверка занятого имени до create, `USAGE` + `existing_id`; Kafka/Redis список — все страницы по `next_page_token` (`dbaas/client.go:166`); PG — одна страница `/v1/clusters` (известное «первые страницы», v1.1).
- `pg_create`: `instances` против `max_hosts`/режима спецификации; `cluster_id` из операции; `pg_delete` превью с GET, `FAILED`/`DEPLOYING` — честные подсказки (DB-21).
- Стек: `stack_plan` резолвит `vm.image`/`vm.zone` до создания чего-либо, закрытая зона — отказ; Redis-форма, Kafka brokers, k8s master_count проверяются на плане; `stack_destroy` превью перечисляет ресурсы и проверяет проект; `deleting` отделено от `deleted`; прерванный create → `Interrupted` и усыновление с проверкой времени для VM.
- `destroyPollTimeout` 2 мин: MCP-ответ `partial` не освобождает FIP при живой ВМ.
