## Правки (файл — что не так — как исправить)

1. **[medium]** `docs/troubleshooting.md` (раздел «Ключ и права») — нет статьи про самую частую ошибку первого запуска после R-06: `CONFIG_INVALID` (код 2) «не задан проект (project_id)». `configure` список проектов сервисному аккаунту не показывает, UUID вводится вручную — коллега, пропустивший этот шаг, получит код 2 на `evo vm list` и не найдёт объяснения. Добавить статью: заголовок `### CONFIG_INVALID (код 2): «не задан проект (project_id)» (no project is set)`, текст — где взять UUID (консоль → сведения о проекте, `auth.md#4-uuid-проекта`), три способа задать (`evo configure --project-id <UUID>`, `CLOUDRU_PROJECT_ID`, `evo project use <UUID|имя>`), что каталоги (`list-zones`, `image list`, `vm flavors`) работают и без проекта, а `doctor` в этом случае выходит с кодом 2.

2. **[medium]** `docs/troubleshooting.md:110-120` («`destroy` ждёт…») — описан только отказ 409/422 «пока нельзя удалить»; нового исхода нет: «Cloud.ru принял удаление ВМ …, но через 2m0s она всё ещё есть; floating IP и правила портов оставлены, запись сохранена (destroying)» (код 5; у MCP `destroy` — `status: partial`). Добавить абзац: это не ошибка evo, ВМ удаляется облаком дольше 2 минут; проверить `evo vm get <id>` и повторить `evo destroy` — он освободит IP и закроет порты; `.evo/state.json` до этого не трогать. Аналогично одно предложение про `provision`/`vm create`: `status: partial` «ВМ работает, публичный IP не привязан» → `fip_attach` или `destroy`.

3. **[medium]** `README.md:17` — «`evo mcp` по stdio или Streamable HTTP, в том числе из Docker-образа» обещает образ, а `docs/mcp.md:605-607` честно говорит, что публичного адреса реестра ещё нет и образ публикуется только при заданных секретах `CLOUDRU_AR_*` (`release.yml`, `RELEASING.md`). До тега либо задать секреты AR и проверить job `image` на rc-теге (R-01 исправлен, но живого прогона job ещё не было), либо в README написать «из Docker-образа (собирается `docker build`, см. mcp.md)». Иначе первый же коллега с Docker упрётся в отсутствие образа.

4. **[low]** `docs/mcp.md:468-470` — «следующий сразу получает ошибку инструмента «server busy» — повторите позже» без кода; назвать `reason: SERVER_BUSY` здесь же (код описан только в `:115`), чтобы оператор HTTP-сервера связал лог с таблицей exit-codes.

## Проверено без замечаний

- **Установка с нуля.** Linux/macOS: одна команда, sha256 и cosign описаны честно, `INSTALL_DIR`, `PATH`-подсказка, Gatekeeper; Windows: пошагово (zip, `Get-FileHash`, `Path`), ограничение «установщика нет» названо в guide §11; ручная установка и проверка подписи — рабочие команды, identity совпадает с `install.sh`.
- **Ключ и проект.** guide §1 и §3 → auth.md §1–5: сервисный аккаунт, ключ, роли (с оговоркой, что минимальный набор не опубликован), UUID проекта, `configure`, профили, переменные (`CLOUDRU_*`, `EVOLUTION_*`, приоритеты), что хранится на диске, ротация.
- **Первый деплой.** guide §5: `init → deploy --dry-run → deploy → verify → logs → destroy`, честные ограничения (только compose-файл, порт 22, зоны, SG общая, DNS подсети), «пока ВМ существует, она оплачивается».
- **MCP.** `claude mcp add --transport stdio … -- evo mcp`, `.mcp.json`, Cursor; HTTP: токен, `--allow-project`, лимиты, политика kubectl (включая `--kuberc`), Docker-запуск с томом; контракт ошибок и `-32602` описаны и совпадают с кодом (этап 3).
- **Ошибки.** exit-codes.md покрывает новые коды и исходы (R-06, partial, 409, destroy unconfirmed, SERVER_BUSY); troubleshooting — AUTH_*, 403, зоны, 409/422, порты, SSH, квоты, 429, UNREACHABLE, UNHEALTHY, k8s/S3, что приложить и чего не прикладывать в обращение.
- **Флаги.** Все примеры команд в README/docs соответствуют `--help`; описания `k8s plan/create/add-nodepool`, `pg create --instances`, `vm delete` в commands.md обновлены вместе с кодом.
